## D-015 — 2026-09-08 — stats.js library conventions
(1) Invalid arguments throw `RangeError` with a `stats:` prefix, so a demo bug fails loudly in tests instead of producing NaN silently; demos are responsible for bounding inputs (SPEC D6). (2) Descriptive functions return `NaN` for empty input (and sample variance for n < 2) rather than throwing, so a demo with no data yet can render a blank readout. (3) `stats.seed(int)` switches every draw to a seeded mulberry32 stream and `stats.unseed()` returns to `Math.random()`; live demos never seed, tests always do, so distributional tests are reproducible. (4) `mode` follows OpenStax §2.5: returns all tied modes ascending, and `[]` when every value occurs once. (5) erf/erfc use Abramowitz & Stegun 7.1.6 (series, |x| ≤ 1.5) and 7.1.14 (continued fraction above), giving tail relative precision ~1e-15 so later p-values stay honest. (6) Poisson sampling uses Knuth's method for λ ≤ 30 and sums chunks above, staying exact without underflow. (7) Test cases live in `tests/stats.test.js`, loaded by `tests/index.html`; one `<file>.test.js` per library file from here on (additive to HANDBOOK §4).

## D-019 — 2026-09-08 — Pilot demo pattern (coin flip) — conventions every later demo copies
(1) **File shape:** constants → state object → controls → chart + marks → pure update functions → one `render()` that redraws everything from state → animation loop → initial state → returned api. The header comment names the syllabus section, the init function, and every stats.js/ui.js function used. (2) **Never empty (D5):** the demo performs `INITIAL_FLIPS` = 10 draws on init, and Reset returns to that same freshly-drawn state rather than to zero. (3) **Honest comparison (D3):** changing a parameter that defines the experiment (here p) clears the run and restarts it, so displayed statistics always refer to the parameter shown. (4) **Rare rescale (D7):** the x-axis extent doubles (100 → 200 → 400 …) when data outgrows it; the rescale is instant — animating a path whose point count changed draws nonsense frames. (5) **Bounds (D6):** a hard cap (100 000 flips) disables inputs and shows a note; Reset stays enabled. (6) **Performance (D9):** long series are thinned to ≤ 2 000 path points, always keeping the last point; measured 0.4 ms per frame at 6 000 flips. (7) **Reduced motion:** the auto loop swaps requestAnimationFrame (1 flip/frame) for a 250 ms interval of 15 flips, same throughput, stepped display. (8) **Colour is never the only cue:** heads are filled coins with an "H", tails hollow with a "T". (9) **Primary action:** the single most important button (Flip 1) is the one primary button; play/pause-style toggles are secondary and relabel themselves. (10) **Testable api:** init returns `{ flip, setP, reset, startAuto, stopAuto, state, constants }` and tests recompute every readout from the raw outcomes; this, plus the `--eval`/`--reduced` modes of tools/gates.mjs, is how D1–D9 are asserted rather than eyeballed. (11) The chapter HTML calls `demos.init…` in a one-line inline script after the demo file (HANDBOOK §6).

## D-020 — 2026-09-08 — Draggable SVG objects, decorative animation, and a two-state toggle (Chapter 3 patterns)
(1) **Draggable marks are keyboard-operable:** each draggable `<g>` gets `tabindex="0"`, `role="button"`, an aria-label that names the arrow-key alternative, and a keydown handler moving it by a fixed data-unit step; positions clamp to the sample space so neither pointer nor keys can push an object out of bounds. `touch-action: none` on `.draggable` keeps phone drags from scrolling. (2) **Decorative animation never carries state:** in §3.3 the counts, table, and readouts update synchronously on every drop (D2/D3); ball animation replays at most 25 balls per drop call, never more than 60 live balls in the DOM in total (a per-call cap alone let 20 fast clicks reach 500), and is skipped entirely under reduced motion. Steady-state DOM cost during auto-drop is ≈ 26 live balls. Labels sit beside nodes, never on the ball path. (3) **Two-state toggle:** a `ui.button` with `aria-pressed` toggled by the demo, plus `.is-dimmed` / `.is-focus` classes on the affected marks and table rows, is the pattern for "condition on / restrict to" controls (and for D-006's mode toggle in §12.1). A `ui.toggle` factory is deferred until a third demo needs it. (4) **Empty-branch guard:** a conditional probability whose denominator is zero renders "—" (via `ui.formatNumber(NaN)`), never NaN or Infinity (D6). (5) **Uniform scale for geometric demos:** when circles must stay circular, the demo computes one px-per-unit scale from the frame and centres the space, instead of using separate x/y scales. (6) Testing note: d3-drag suppresses the click that immediately follows a drag; scripted gate runs must not click synchronously after a simulated drag.

## D-021 — 2026-09-08 — Canvas layer and theme-token reader in ui.js; init-order rules for demos
(1) `ui.canvas(frame)` adds a `<canvas>` under a chart frame's SVG, sized to the plot area and scaled for the device pixel ratio, so dense dot fields (D-007) keep the SVG for axes, markers, and pointer events. `ui.token(name)` reads a theme custom property once so Canvas code never hard-codes a colour; the grep audit treats `fillStyle`/`strokeStyle` assignments not fed by `ui.token` (directly or via an array of tokens) as violations. Both were added in Phase 6 because D-007 requires Canvas here; both have tests. Any SVG shape drawn over a canvas layer must be unfilled (`.space--open`): a filled sample-space rectangle hid every dot in §1.2 until the screenshot gate caught it. (2) **Init order:** `frame.onResize(fn)` calls `fn` synchronously, so anything a demo's `render()` reads must exist before the chart is built — constant tables go at the top of `init`, and `render()` returns early while the population is empty. A `var` declared later in the function is hoisted but still `undefined` at that moment; Phase 6 hit this once and it silently killed the rest of the chapter's inline init script. (3) **Never write NaN into SVG attributes:** hide a marker and skip its attribute writes when its value is not finite; d3 scales map NaN to `undefined`, which the browser logs as an attribute error. (4) **The truth stays put:** in §1.1 and §1.3 the population is generated once per page load and only changes via an explicit "New population" button; Reset keeps the population and restores sample size and history. (5) §1.2's convenience sample is deterministic (the n residents nearest a marked entrance), so its bias is reproducible on every draw; stratified allocation uses proportional quotas with largest-remainder rounding.

(1) **Draggable points on lanes:** a set of values on a number line is drawn as one point per lane (rows 26–30 px apart) so points never hide each other; each is a `<g role="slider" tabindex="0">` with `aria-valuenow/-valuetext`, an invisible 44 px hit circle (SPEC §6), pointer drag via d3-drag, and arrow keys stepping one unit. §2.2 rounds values to integers so equal values (a mode) are reachable; §2.4 keeps values continuous so bunching can reach zero spread. (2) **Fixed datasets are pasted literals:** §2.1's 80 commute times were generated once (NumPy, seed 20260908) and committed as an array, so every student sees the same shapes and the reference histogram in the tests is exact. (3) **D-004 constants:** σ = 9, μ₁ = 50 − 10 s, μ₂ = 50 + 25 s, w₂ = 0.35 |s| for s ∈ [−1, 1]; each point stores its own (z, u) so the slider morphs the same 300 points; the histogram's y-axis is fixed at 80 (never exceeded at N = 300), and the box plot's whiskers run to min and max as in OpenStax. (4) **Histogram axes:** when the bin width itself is the control (§2.1), the y-axis rescales to the tallest bin rounded up to a multiple of 5 — that rescale is the lesson, so D7's "rarely" does not apply. (5) **`tools/lint-demos.mjs`** mechanically enforces D-021 §2 (no init-scope table declared after the first `onResize` and used in `render()`), the header-comment contract, and the single `demos` global; the init-order bug recurred in §2.1 despite the written rule, which is why it is now a tool. (6) Reminder for scripted gates: any click issued synchronously after a simulated d3 drag is swallowed (D-020 §6); run such checks in a separate evaluation.

## D-023 — 2026-09-08 — Chapter 4: moments from PMF tables, display windows, and the geometric convention
(1) **Moments come from the PMF table, not from per-distribution closed forms.** §4.3 builds each distribution's table (k, P(k)) until the remaining tail is below 1e-14 (or the finite support ends) and feeds it to the already-tested `stats.expectation` / `stats.discreteVariance`. This keeps stats.js small (no eight trivial mean/variance functions), and the tests assert the table moments against the closed forms to 1e-9 for all four distributions. (2) **Display window:** a finite support (binomial, hypergeometric) is drawn whole, empty tail bins included, because "these values are possible but rare" is part of the lesson; an infinite support (geometric, Poisson) is drawn up to the last k with more than 0.2 % of mass beyond it. Both are capped at 60 bars, and draws that land beyond the window are counted in a "Draws beyond the axis" readout so nothing is silently dropped (D3). (3) **Geometric convention:** X counts trials up to and including the first success (support 1, 2, …), matching OpenStax §4.4 and `scipy.stats.geom`; `sampleGeometric` is the literal loop of Bernoulli trials, and `sampleHypergeometric` draws one item at a time without replacement — both are the definitions, not shortcuts. (4) **Loaded-die guard:** weights 0–10 normalise to probabilities; setting the last non-zero weight to zero snaps it back to 1 so the table never divides by zero (D6). (5) **Theory vs empirical bars** share each integer slot, theory on the left in `--accent-soft` with an `--accent` outline and draws on the right in `--accent-strong`; position and shade both carry the distinction, and a legend line names them. (6) **Probability axis for the die charts:** the y-axis tops out at max(0.6, largest P(x) rounded up to 0.1) — driven by the theoretical table only, so it never jitters as rolls accumulate (D7); an early empirical proportion above the top is clipped for the few rolls it lasts.

## D-024 — 2026-09-08 — Chapter 5 patterns: density-scaled histograms, interval handles, and the memoryless comparison
(1) **Density-scaled histograms:** when draws are shown under a density curve, bar height is count / (n · bin width), so the histogram converges to the curve on the same axis and the picture itself teaches what a density is. Draws beyond the fixed axis are counted in a readout (as in D-023 §2). (2) **Interval handles:** the two ends of an interval are draggable, keyboard-movable SVG groups (D-020/D-022 pattern) that clamp to the axis and push each other rather than cross; values are rounded to 0.01. Moving a handle restarts the draw count, because the "share inside" readout must count every draw against the current interval and values that fell beyond the axis are not kept individually (D3). (3) **Uniform width floor:** b − a ≥ 0.5 so the density never exceeds 2 and the y-axis stays readable; the other end follows when the floor is hit. The density y-axis tops out at max(0.5, peak rounded up to 0.25), driven by the parameters only (D7). (4) **Memorylessness is shown four ways:** the conditional density of the remaining wait drawn as the original curve shifted by t; the theoretical P(W > t + 1 | W > t) beside P(W > 1) (always equal); and the same two shares computed from the observed waits. Arrivals are simulated as a running sum of exponential waits, so the timeline and the histogram come from the same numbers. (5) Initial state for §5.1 is the curve with the shaded default interval and no draws — the density itself is the meaningful default (D5); §5.2 starts with 5 arrivals.

## D-025 — 2026-09-08 — Chapter 6 patterns and the execution-order lint
(1) **Comparing two normals:** §6.1 uses two fixed-axis charts (0–100 and 200–800) plus one shared standard-normal chart; each score is a draggable, keyboard-movable handle (D-024 pattern) and both land on the z axis by their z-scores, with a verdict line naming which score stands higher. ## D-026 — 2026-09-08 — Chapter 7 patterns: honest overlays, simulation-verified constants, and the SE sweep
(1) **Overlays are theory, never fits:** the normal curves in §7.1 and §7.3 are N(μ, σ/√n) and N(nμ, σ√n) computed from each parent's closed-form μ and σ, drawn before any sample exists; the text says so. (2) **Parent constants are tested by simulation:** the five parents (flat, skewed exponential with mean 2, two-hump normal mixture, arcsine U-shape via 10·sin²(πU/2), and a die) each carry a cited μ and σ, and a test draws 20 000 values from every parent and checks both to within sampling error — the D10 verification for numbers that are not stats.js functions. (3) **Shared parent table, three files:** the parent definitions are repeated in each demo file rather than hoisted into a shared module, per "one demo, one file" (HANDBOOK §1.3); the simulation test guards them all through §7.1's api. (4) **Standard-error sweep:** each point is the sample SD of 2 000 simulated sample means at one n (≈2 ms at n = 100), so the whole 12-point sweep runs in a few milliseconds and the dots visibly sit on σ/√n for every parent; the current n keeps its own point, so a sweep can show 13 dots. (5) **Sum axis:** §7.3 centres its axis on nμ ± 5σ√n, clipped to the smallest and largest possible sum, and changes it only with n or the parent (D7); sums that would fall outside are counted, not dropped. (6) Density-scaled histograms and the "orange overlay" convention (`--cat-2`, class `line--overlay`) are now the site-wide look for "what the theorem predicts".

## D-027 — 2026-09-08 — Special functions by textbook algorithms; quantiles by bisection; Chapter 8 patterns
(1) **Algorithms:** `logGamma` is the Lanczos approximation with g = 7 and nine coefficients (Godfrey 2001, as in Numerical Recipes 3rd ed. §6.1) with the reflection formula below 0.5; `incompleteBeta` is NR3 §6.4's `betai`/`betacf` (modified Lentz continued fraction, ε = 1e-15, up to 1000 terms); `tCdf` uses I_{ν/(ν+t²)}(ν/2, ½). Each is tested against SciPy, with tiny values (down to 1e-10) checked relatively. (2) **Every inverse is bisection:** `tQuantile` and `normalQuantile` expand a bracket by doubling and then halve it 100 times on the tested CDF. It is slower than a rational approximation but has no coefficients to get wrong, converges to ~1e-15, and passes the same SciPy references; F and χ² inverses (Phases 16, 18) will reuse the same helper. Demos call quantiles only when a slider changes, never per frame. (3) **Stacked-interval view:** the last 40 intervals are drawn newest-first as segments with a dot at the estimate, misses in `--warn` and dashed (shape + colour); totals count every interval ever drawn, so the capture rate is honest beyond what is visible. Changing the level or n starts a new run (D-019 §3). (4) **§8.2 shows both intervals on one sample** (z with σ known, t with s) so the extra width of t is seen as a price, not an abstraction; the status line names the rare case where s fell below σ and the t-interval came out narrower. (5) **§8.3 uses the Wald interval exactly as OpenStax §8.3 states it** and does not hide its failure: when n·p or n·(1 − p) is below 5 the status line warns and the capture rate visibly falls short (asserted in a test). A zero-count poll gives a zero-width interval, never NaN. (6) A fixed count axis chosen as "never exceeded" must clear the tallest bar by several standard deviations, not merely on average (§2.3's 80 became 100 after a 2 % flaky failure).

## D-028 — 2026-09-09 — Chapter 9 patterns: known-σ z-tests for the ideas, a t-test for the procedure, truth-aware verdicts
(1) §9.1 and §9.2 use the z-test with σ = 10 known so the sampling distributions are exact normals and α, β, and p come straight from `normalCdf`; §9.3 uses the one-sample t-test with σ unknown, as OpenStax §9.5 does, so the procedure students will actually run is the one shown. (2) **The demo knows the truth, the test does not:** each demo has a "what is actually true" control (an effect slider, a true/false toggle, a true-mean slider) that the simulated test never reads; the verdict line then names each decision as correct, Type I, or Type II, which is the only way to make error rates concrete. (3) **α is one-sided in §9.1** (H₁: μ > μ₀) so a single cutoff carries the whole trade-off; §9.2 and §9.3 are two-sided, and §9.2 draws the mirror point of x̄ as a hollow marker so both shaded tails read as one p-value. (4) **The flat line:** §9.2's p-value histogram carries a reference line at 1/20 — the uniform distribution p-values have under a true H₀ — because "5 % of true nulls are rejected" is the same fact as "p is uniform under H₀". (5) Precision rule: values that feed the mathematics (the cutoff) are stored at full precision and rounded only in readouts and aria values; rounding in state made "α = 5 %" read 5.01 %. (6) Sliders for a "truth" that must be able to equal μ₀ exactly use a step that hits μ₀ (0.5 here), so the "H₀ really true" case is reachable.

## D-030 — 2026-09-09 — Chapter 10 patterns: tests as library functions, Welch by default, and two-chart panels
(1) **Every test statistic is a stats.js function** returning `{ t | z, df, p }` (`welchTest`, `pairedTest`, `twoProportionTest`), tested against SciPy or an independent hand computation, so demos never assemble a formula inline; Chapters 11 and 13 will follow the same shape (`chiSquareTest`, `anovaTest`). (2) **Welch, not pooled-variance:** §10.1 uses Welch's t (OpenStax's Aspin-Welch) and says so in a footnote; the H₀ curve on the second chart is the known-σ N(0, σ√(2/n)) because it is exact and the lesson is about noise, while the p-value comes from the samples' own s. The mismatch is stated in the legend. (3) **Two-proportion edge:** when the pooled proportion is 0 or 1 the standard error is zero; the function returns z = 0, p = 1 ("no evidence either way") rather than NaN, and the test asserts it (D6). (4) **Paired vs independent on identical data:** §10.3 keeps one dataset and switches only the analysis, showing both p-values at once and joining subjects with lines only in paired mode, so the effect of pairing is seen as a change of method, not of data. The subject model (between-subject SD 12, within-subject SD 3) is chosen so pairing wins in ≥ 90 % of redraws, which a test asserts. (5) **Side-by-side charts** (`.chart-pair`, 1 column under 40 rem) are the pattern when a demo has a "this run" view and an "all runs" view; both are built before the first resize registration per D-025.

## D-031 — 2026-09-09 — Chapter 11 patterns: fair die vs claimed die, D-005 verified by margins, tables on phones
(1) **Which side is editable:** §11.1 keeps the real die fair and lets the student edit the CLAIM. When the claim is fair, H₀ is true and the χ² pile follows χ²(5); a wrong claim is a false H₀ and the pile slides right with n. This is the reverse of the everyday story (claim fair, die loaded) but makes both the null distribution and power visible from one control, and the status line says which case is in play. Claimed weights have a minimum of 1 so every expected count is positive (D6); an expected count below 5 triggers the OpenStax warning. (2) **D-005 is enforced by tests:** the independence table is (1 − s)·P_indep + s·P_assoc with P_assoc chosen to share P_indep's margins exactly; a test walks s from 0 to 1 in steps of 0.05 and checks non-negativity, sum to 1, and all five margins. So association is the only thing the slider changes. (3) **Row profiles, not a mosaic:** independence is shown as two stacked bars of column shares, one per row — identical bars mean independence — with percentage labels inside segments wide enough to hold them. (4) **χ² statistics beyond the fixed axis** are counted in `beyond` and the marker label says "(off the axis)" rather than clamping silently. (5) **Wide content on phones:** a five-column table overflowed a 360 px page for the first time; `.section__demo` now scrolls its own overflow (SPEC §6: wide content must scroll inside its container) and table cells use half padding below 30 rem. The 360 px gate now checks `document.scrollWidth` on every chapter as before; this was the first time it fired.


## D-032 — 2026-09-09 — Chapter 12 patterns: 2-D draggable points, literal squares, deterministic presets, a fit that degrades to blanks
(1) **Two-axis draggable points** extend D-020/D-022: `<g class="point draggable" tabindex="0" role="button">` with a 44 px hit circle, d3-drag reading both `event.x` and `event.y`, and arrow keys moving x (Left/Right) and y (Up/Down) by a fixed step; `role="button"` rather than `slider` because a 2-D position has no single `aria-valuenow`, and the aria-label restates both coordinates on every render. (2) **D-006 implemented as mutual exclusion:** in "line" mode points get `is-inert` (pointer-events none, tabindex −1) and their key handler returns early; in "points" mode the line handles are `display: none` with tabindex −1 and their handler returns early. Tests assert both directions, so the two drags can never fire together on touch. (3) **Residual squares are pixel squares** whose side is the residual on the y scale, so areas are proportional to squared residuals on screen even though the x and y scales differ; each square extends toward the plot centre so it stays inside the frame. The student's line is defined by two handles at fixed x (1.5 and 8.5), which keeps both handles on screen and avoids intercept/slope sliders. (4) **Deterministic presets** in §12.2 come from one fixed noise vector scaled per preset, so "steep" and "shallow" are affine images with exactly equal r, and the parabola is centred on x̄ so r is exactly 0; tests assert both identities rather than approximate values. Dragging any point switches the preset to "custom" with no button pressed. (5) **`linearRegression` throws when every x coincides** (as `scipy.stats.linregress`) and returns `r = NaN` for a constant y (as `numpy.corrcoef`); demos wrap the call and render "—" readouts, hide the line, and draw no squares, so an all-points-on-one-x drag never writes NaN (D6, D-021 §3). `sumSquaredResiduals` exists as a public function so the manual-line SSE is computed by the same code as the fit's own SSE. (6) **The population line in §12.3 is the population's own least-squares fit**, not the generating formula, because the cloud is clamped to the axes; the target the band converges on is therefore exact for what is on screen. (7) Testing note: `ui.readout` values carry `role="status"`, so demo tests must query `.demo__status[role=status]` for the prose status line.

## D-033 — 2026-09-10 — Chapter 13 patterns: the handle is the group mean, F on fixed axes, and rescale comparisons need headroom
(1) **Dragged means over centred residuals.** In §13.1 each group's points are `mean + spread × z`, where the `z` are standard normal draws with their own mean subtracted. The group mean is then exactly the handle a student drags, so `aria-valuenow` is honest and dragging changes only the between-group term while the within-group term holds still — which is the whole lesson. Every printed quantity still comes from `stats.anovaTest` on the points actually plotted (D3); the construction fixes what the data are, not what is computed from them. §13.2 draws its data the ordinary way, without centring, because there the sampling distribution is the point. (2) **§13.2 makes its own observed F.** The syllabus asks for "the observed F from 13.1", but reading another demo's state would couple two files and break the one-demo-one-file rule (D-019). Instead §13.2 owns a true-gap slider: at gap 0 the histogram fills the F curve and ≈ 5 % of studies cross the critical value, and any positive gap slides the pile right, which also buys a power story that the original wording did not have. (3) **Fixed F axis with an off-axis counter.** The F axis stays at 0 to 8 because that is where the null distribution lives (D7). A strong effect pushes studies past it, so a "Past the axis" readout counts them and the status line says outright when every study has left the frame — no silent loss (D6). The density y-axis is fixed at 1.25 because with three groups df1 = 2 always, and the F(2, ·) density is exactly 1 at the origin for every df2. (4) **Rescale comparisons must not sit on the boundary.** The mean-square axis doubles while `biggest > msMax × 0.85` rather than `>= msMax`. With the default data the between-group mean square lands on 40.0 to within floating-point noise, and an exact-tie comparison flipped the axis between two values from run to run. Any doubling or halving rule needs a margin between its trigger and the value it is compared against.

## D-036 — 2026-09-10 — Chapter 15 patterns: icon arrays that fit, likelihood as a shape, and notation that does not collide
(1) **The icon array sizes itself to the frame.** 1 000 dots at a fixed 11 px cell filled less than half the panel at desktop width and would have overflowed at some narrower ones. The layout now starts from the cell that would tile the available area exactly, `sqrt(width × height / N)`, takes the column count that implies, and shrinks the cell until the resulting rows also fit. Groups are drawn as four contiguous blocks in reading order and named by a count table beside the array, so a reader tells them apart by position, not colour (SPEC §6). (2) **Head count and exact probability are both shown.** The array holds whole people, so its proportions are rounded; the readouts carry the exact Bayes figure from `stats.diagnosticTest` and, separately, the array's own count of positives and true positives. The tests assert the two agree to rounding. Showing only the rounded version would misstate the maths, and showing only the exact version would leave the picture unaccounted for. (3) **A likelihood is not a density and its axis says so.** §15.2 rescales the vertical axis to the curve's own peak, which D7 otherwise discourages, because likelihood values shrink towards zero as n grows and only their ratios carry meaning. The legend states the rescaling. The ratio readout switches to exponent form past 1 000, since a candidate far from k/n is worse by factors like 3.2e+63 and printing that in full is noise. (4) **Symbols are checked against the rest of the site.** The first draft of §15.3 wrote the posterior as Beta(a + s, b + f); `check-prose.mjs` flagged it as an undocumented use of s, which is the sample standard deviation everywhere else on this site. ## D-037 — 2026-09-10 — Chapter 16 patterns: a permutation p-value is never zero, and probabilistic tests need probabilistic margins
(1) **p = (1 + extreme) / (1 + shuffles).** The first draft divided the tail count by the number of shuffles, which reports p = 0 whenever a real effect is large — a claim no finite run of shuffles can support. The observed labelling is itself one of the arrangements the null hypothesis allows, so it belongs in both counts. The demo, the status line and the printed formula in §16.2 all use the corrected form, and the section says why the ones are there. (2) **A test that asserts about randomness must allow for it.** Two assertions failed on their first seeded run, not because the demos were wrong but because the tests were: "a smaller sample has a larger standard error" compares s/√n across two single draws, and s varies enough at n = 5 to reverse it, so the test now averages fifteen fresh samples at each size. "A 6-point gap on n = 12 is detected" asked for p < 0.02 when that setting gives roughly 1.8 standard errors and a typical p near 0.07; the assertion moved to a 12-point gap at n = 40, which is beyond every shuffle. The rule for this project: an assertion about a random quantity states the margin it tolerates and is checked against the distribution it is really sampling from, not against one hopeful run. (3) **Resampling is shown, not asserted.** §16.1 stacks the latest resample's picks above the values they came from, so a value drawn three times is a column of three and a value missed is a gap. That the same value can appear twice is the part students disbelieve, and a readout cannot settle it. Stacks taller than the strip clamp to the top row rather than drawing outside the plot; the mean still uses every pick. (4) **Careless global replacement is a real hazard.** One edit in this phase matched an identical line in the Chapter 9 test file and silently broke it; the suite caught it immediately. Edits into a large shared test file must anchor on text unique to the block being changed.

## D-038 — 2026-09-10 — Chapter 17 patterns: the lurking variable is a control, and the 3 × 3 solve is written out
(1) **Simpson's paradox is produced, not staged.** §17.1 gives both groups the same within-group slope, which the student sets, and offsets their centres along a line running the other way. The separation slider is the lurking variable made into a control: at zero the pooled line matches the groups, and past about half the range it reverses them. Nothing is special-cased — every line on screen is `stats.linearRegression` on the points actually plotted, and the tests fit them independently to confirm it. Groups are filled versus hollow marks, so pressing "Ignore the groups" removes a visible cue rather than a colour (SPEC §6). (2) **The normal equations are solved by hand.** `stats.twoPredictorFit` builds the 3 × 3 system from the eight sums it needs and applies Cramer's rule, per PLAN A1's instruction to write the solve rather than add a dependency. Collinear predictors make the determinant vanish, and the function returns null instead of dividing by something near zero; the demo then blanks its readouts and shows a note (D6). The determinant threshold is scaled by the size of the system's entries, since an absolute cutoff would be meaningless across different data ranges. (3) **Both fits are drawn through the same centre.** §17.2 plots y against x₁ only, so the two-predictor b₁ has no natural line on that plot. Drawing it through the point of means makes the comparison honest: the two lines differ in slope alone, which is the only thing being compared, and the legend says that is what was done. (4) **The chapter states that neither answer is wrong.** A coefficient that changes when a predictor is added has not been corrected; it has been asked a different question. The plain-English readout names the condition — holding x₂ fixed — every time it prints a number.

## D-039 — 2026-09-10 — Final hardening: defer every script, and ship the static chrome in the HTML
(1) **`defer` on every classic script.** They already sat at the end of `<body>`, but a parser-blocking script blocks regardless of position, and the vendored D3 alone cost an estimated 2.7 s under Lighthouse's throttling. `defer` preserves execution order, which is what the `d3 → stats → ui → chapters → site → demos` chain needs, and keeps the classic-script model of D-012/D-013 intact — no modules, no build step. (2) **Static chrome belongs in the HTML.** The chapter header, the chapter nav and the landing card grid are fixed text derived from `chapters.js`, and building them after first paint was the site's largest layout shift as well as what held the largest-contentful-paint past three seconds.
